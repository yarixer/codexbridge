# Yarocursor: план перехода от прототипа к рабочему продукту

Дата: 13 сентября 2026. База: v0.2.0, commit `42caff2`.
Статус: план разработки. Описанные ниже новые возможности пока не реализованы.

## 1. Цель и границы

Создать desktop-приложение для Windows и Linux с интерфейсом и поведением агентной части Cursor: проекты, постоянные чаты, живые действия агентов, модели, Rules, Skills, поиск, настройки, просмотр и принятие результата. Название — Yarocursor.

Основной сценарий: выбрать или создать репозиторий → написать сообщение → видеть работу агентов → проверить результат → применить изменения → продолжить разговор. Подключения настраиваются один раз.

Базовый профиль остаётся прежним: GPT-6 Astra через подписку ChatGPT/Codex планирует и проверяет, Grok 4.6 xHigh Fast через Cursor SDK реализует. Роли сохраняются при выборе других доступных моделей. Astra не получает права изменять код проекта.

Визуальный ориентир — [Cursor Agents Window](https://cursor.com/docs/agent/agents-window). Переносим композицию, плотность, навигацию, поведение чата и управления агентами. Собственные название и значок Yarocursor. Исключены IDE, редактор кода с расширениями, debugger/LSP и MCP. Просмотр файлов, diff, изображений и вывод команд остаются частью результата агента. Простой редактор текста Rules/Skills — часть настроек.

Облачные VM, SSH, Marketplace, командные аккаунты и отдельный сервер синхронизации не входят в первую полную версию. «Как Cursor» в этом плане означает перечисленные агентные сценарии на локальных репозиториях.

## 2. Что уже доказано и что нужно заменить

Сохраняем Rust/Tauri, интеграции с провайдерами, Git worktree и SQLite. Перерабатываем экран приложения, модель чатов, жизненный цикл запуска и передачу событий.

| Сейчас | Целевое поведение |
|---|---|
| Главная страница — диагностика и форма задачи | Главная страница — проекты и чат; диагностика внутри настроек |
| Один восстановленный последний TaskSession | Проекты, много чатов, история сообщений, отдельные запуски внутри чата |
| Cursor `server_stream` читает весь `response.bytes()` | Инкрементальный разбор фреймов и немедленное отображение событий |
| В запросе отключены `enableDeltas` и `enableSteps` | Адаптер выбирает и согласует доступные текстовые события и шаги без дублей |
| Astra создаёт временную thread и удаляет её | Постоянная сессия архитектора с управляемым сжатием контекста |
| Модели и effort прописаны в коде | Каталог провайдера, сохранённые настройки по роли/проекту/чату |
| Cursor key хранится только в памяти | Системное хранилище секретов и автоматическое восстановление |
| Повторные попытки считаются неоднозначно | Отдельный учёт запусков, транспортных повторов, итераций исправлений и ревью |
| Отсутствие визуального доказательства означает «нужна доработка» | Отдельная причина «нужны доказательства» и действие для их получения |
| Результат остаётся в длинном пути AppData | Список файлов, открыть/запустить, diff, применить в выбранную ветку |

Основание: `src/App.tsx`, `src-tauri/src/lib.rs`, `crates/yarocursor-core/src/{cursor,codex,orchestrator,store,validation,git}.rs` и результаты уже проведённого пользовательского теста. Текущий успешный обмен Astra → Grok → проверки → Astra доказывает работоспособность интеграций, но не готовность ежедневного интерфейса.

## 3. Интерфейс

### Компоновка

| Область | Содержание |
|---|---|
| Левая панель, изменяемая ширина | Новый чат, поиск, проекты; внутри проекта список чатов со статусами; закрепление, архив; Rules, Skills, Настройки |
| Верхняя строка | Название чата, проект/ветка, режим работы, состояние выполнения; меню действий |
| Центр | Единая лента: пользователь, Astra, Grok, сообщения системы, команды, изменения, проверки и ревью |
| Нижний composer | Многострочный ввод, вложения, `@`-контекст, `/`-skills; режим, модели, effort, Fast, контекст; отправить/остановить |
| Правая панель, сворачиваемая | Вкладки «План», «Изменения», «Результаты», «Проверки»; предпросмотр файла/diff/картинки |

Настройки и подключения не занимают постоянную половину экрана. Пустой чат приглашает написать задачу. У задачи всегда видны папка результата и текущий этап. Статус Astra не исчезает, если она ещё не начала ревью.

### Темы и визуальная приёмка

Белая, чёрная и системная темы; выбор сохраняется. Общие токены цветов, типографики, отступов, границ, hover/focus/disabled и статусов. Для чёрной темы — нейтральный почти чёрный фон, для белой — белый фон с отдельными оттенками панелей. Начальные размеры для макетов: sidebar 240–300 px, правый inspector 320–420 px, основной текст 13–14 px; уточняются сравнением с эталоном.

Перед реализацией экранов зафиксировать референсы одной версии Cursor: пустой проект, работающий чат, выбор модели, настройки, Rules/Skills, просмотр diff. Подготовить макеты тех же состояний для обеих тем. Использовать небольшие контролы, умеренные скругления, компактные строки действий и читаемые markdown-сообщения. Сравнивать не только цвета, но и геометрию, плотность и поведение скролла.

Проверять 1280×800 и 1920×1080, масштаб Windows 100/125/150%, клавиатурный фокус, контраст и отсутствие горизонтального переполнения. Все видимые кнопки должны работать либо иметь понятную причину недоступности.

### Чат и процесс работы

Сообщения продолжают существующий разговор; заголовок можно переименовать, чат закрепить, архивировать, найти через поиск. Переключение чата не останавливает run. Длинная история загружается частями.

В ленте показываем: кто работает и какой моделью; поступающий текст; доступные reasoning summaries/thinking-события; чтение и поиск файлов; вызовы команд и их вывод; изменённые файлы; пункты плана; передачу задания от Astra к Grok; результаты тестов; вывод ревью. Эти записи сворачиваются, имеют время, статус и ссылки на файлы.

«Что думает агент» означает реально выдаваемые провайдером пояснения и события рассуждения. Полного скрытого внутреннего хода мысли интерфейс не обещает. При отсутствии текста отображается честный статус «Обдумывает», без сгенерированного объяснения от другой модели.

Отправка во время работы: очередь сообщений, отмена сообщения из очереди, доступное провайдеру уточнение текущего запуска. Если live steering не поддерживается конкретным адаптером, сообщение остаётся в очереди с явной пометкой. Кнопка Stop действительно отменяет run; Escape закрывает меню, не отменяя работу случайно.

## 4. Репозитории и результат

Три действия на стартовом экране: открыть существующую папку/repository, клонировать по URL, создать новую папку с Git. Для нового Git без HEAD создаётся необходимая начальная база как часть явно выбранного сценария создания. Проверяются существование папки, права записи, Git и выбранная ветка.

Храним список последних и закреплённых проектов, путь, ветку и настройки. Для dirty checkout предлагаем выбор базы: последний commit или отдельный снимок текущих изменений. Не заставляем пользователя вручную делать stash перед каждым чатом. Работа агента по умолчанию — отдельный worktree, привязанный к чату; следующие сообщения используют ту же рабочую копию. Репозитории с пробелами и кириллицей в пути входят в обязательные тесты.

Результаты показываются сразу после появления: файл, тип изменения, размер, открыть папку, скопировать путь, предпросмотр текста/картинки. Запуск программы оформляется сохранённым действием с командой, cwd и логом; команды не угадываются без подтверждённого рецепта запуска.

Панель изменений: diff по файлу и всей задаче, добавленные/удалённые/переименованные и бинарные файлы, контрольные точки. «Применить результат» показывает целевую ветку и полный набор изменений, затем интегрирует выбранную проверенную версию. При конфликте — понятный список и возможность поручить разрешение Grok в отдельной рабочей копии. Пользовательские незакоммиченные изменения сохраняются. Частичное принятие инвалидирует вердикт на прежний полный diff и требует проверки выбранного набора.

Уборка worktree — отдельное действие после применения/архивации с проверкой наличия несохранённого результата. Архивировать чат не значит удалить его файлы.

## 5. Ключ, подключения и настройки

Сохранение Cursor API key — первый обязательный deliverable. На Windows использовать Credential Manager, на Linux — Secret Service; Rust-адаптер предоставляет `save/read/delete/status`. Ключ хранится у backend, UI получает статус подключения и маску. Повторное открытие приложения не требует ввода ключа. Очистить/заменить ключ можно в настройках. Пустое поле диагностики не должно удалять сохранённый секрет.

На Linux различать «ключ отсутствует» и «хранилище заблокировано/не установлено». Для окружений без Secret Service предусмотреть явно выбранное зашифрованное хранилище с разблокировкой; никакого скрытого перехода на plaintext. SQLite, localStorage, экспорт чата и логи не содержат секрет.

Astra продолжает использовать вход ChatGPT/Codex. Состояние аккаунта читается автоматически; процесс логина принадлежит Yarocursor. Первичная проверка запускается после настройки, далее работает в фоне и по кнопке в настройках. Просмотр проектов, чатов и результатов доступен без подключения обоих провайдеров. Продолжение валидации/ревью не требует Cursor key, если Grok не вызывается.

Разделы настроек: Общие, Внешний вид, Аккаунты, Модели, Контекст, Оркестрация, Rules, Skills, Проекты, Команды проверки, Хранилище и диагностика. Области действия: глобальные defaults → проект → чат; snapshot фактических значений фиксируется на каждом run. Изменения во время работы вступают в силу на следующем turn.

## 6. Модели, effort, упорство и контекст

| Настройка | Семантика |
|---|---|
| Модель архитектора | По умолчанию GPT-6 Astra, доступные альтернативы из Codex model catalog; роль только чтения |
| Модель исполнителя | По умолчанию Grok 4.6; другие модели только из доступного Cursor catalog |
| Глубина рассуждений | Значения, реально предоставленные выбранной моделью; `xHigh` не навязывается всем |
| Fast | Отдельный параметр/вариант, только при наличии в каталоге |
| Упорство | Политика Yarocursor: максимум циклов исправлений, время работы, условия остановки и отсутствие прогресса |
| Контекст | Бюджет передаваемого контекста, политика сохранения истории, сжатия и извлечения файлов |

Предлагаемые профили упорства: одна итерация; стандартный — до трёх циклов исправления; настойчивый — до шести; пользовательские ограничения. Числа — предлагаемые defaults продукта. Сетевой reconnect и сбор отсутствующего доказательства не считаются новым циклом исправления. Повторение одинаковой ошибки без изменения состояния приводит к конкретному запросу помощи, а не бесконечному повтору.

Контекст: Auto и ручной бюджет, например 32k/64k/128k только в допустимом диапазоне выбранной модели. UI различает «бюджет, который формирует Yarocursor» и «реальный предел/режим провайдера». Ползунок не увеличивает модельное окно. Если SDK не предоставляет жёсткого ограничения полного контекста, показываем это и применяем настройку к управляемым вложениям и сводкам. Неизвестный расход обозначается неизвестным, оценка — приблизительной.

В composer — индикатор использованного/доступного контекста, по клику состав: инструкции, Rules, Skills, сообщения, файлы, результаты инструментов, сводка. Часть, скрытая внутри провайдера, помечается как недоступная для детализации. Доступны закрепление контекста и «Сжать историю». После сжатия сохраняются цель, принятые решения, ограничения, незавершённые действия, ссылки на доказательства.

Экономия Astra обеспечивается архитектурой: адресный план и контроль результата, компактные задания Grok, локальный поиск и проверки без LLM, полный лог на диске и нужные фрагменты для ревью. Обрезанный diff не представляется полным: дробление по файлам и явный учёт непроверенных частей. Никаких процентов экономии без замера на одинаковых задачах.

## 7. Rules и Skills

Rules: создать, редактировать, удалить, включить, выбрать глобальную/проектную область и роль Astra/Grok/обе. Режимы: всегда, по файлам, вручную и по релевантности. Для каждого run отображать реально активные правила и причину подключения.

Собственные правила проекта: `.yarocursor/rules/*.mdc`; глобальные — в пользовательском каталоге Yarocursor. Совместимость чтения и импорта с `.cursor/rules/*.mdc`, `AGENTS.md` и существующими legacy rules. Не переписывать чужие файлы автоматически. Порядок разрешения конфликтов фиксируется и показывается пользователю; точные ограничения задачи и политики роли не исчезают из-за импортированного правила.

Skills: каталог, поиск, импорт из локальной папки или Git URL с фиксируемой ревизией, простое создание `SKILL.md`, preview, включение/отключение по области и роли. Канонический совместимый формат — `SKILL.md` и дополнительные `scripts/`, `references/`, `assets/`. Поддержать `.agents/skills/` и импорт `.cursor/skills/`. Сначала агенту доступны названия и описания; полный текст и дополнительные файлы загружаются по необходимости. Ручной вызов `/skill-name`, видимый список активных skills.

Адаптер должен исключать двойную загрузку одних Rules/Skills из native discovery и составленного Yarocursor контекста. Правила, привязанные к файлам, должны применяться и к файлам, обнаруженным уже во время работы. Если native discovery не покрывает нужную область/роль, использовать контролируемый provider-specific пакет инструкций; проверить это контрактным тестом. Возможности skill исполняются через инструменты соответствующего агента, без MCP. Skill с требованием недоступной интеграции отмечается несовместимым.

Форматы и поведение импорта сверять с [Cursor Rules](https://cursor.com/docs/rules) и [Agent Skills](https://cursor.com/docs/skills). Совместимость с форматом не означает автоматическую совместимость со всеми действиями skill.

## 8. Оркестрация, которая доводит задачу до результата

Режимы: «Обсудить», «План», «Выполнить». Первые два не передают исполнителю разрешение писать файлы. Запрос «дай краткий план» завершается ответом в чате. Запуск реализации — явное действие пользователя или заранее включённая политика Agent для этого чата.

В режиме выполнения: Astra уточняет необходимые вопросы и формирует план → Grok работает → локальные проверки → Astra проверяет изменения и доказательства → исправление замечаний/сбор доказательств → итог. После однократного утверждения плана цикл идёт автоматически в пределах упорства и полномочий. Повторный запрос утверждения нужен только для существенного изменения согласованного объёма или отдельного защищённого действия.

Разделить состояния и причины: ожидает утверждения, выполняется, проверяется, ревью, нужны исправления кода, нужны доказательства, нужен пользователь, ограничение провайдера, ошибка среды, остановлено, завершено. В UI — читабельные названия, стадия, причина и конкретное действие; enum-строки SDK остаются в диагностике.

Критерий приёмки имеет id, тип проверки, обязательность и ссылки на доказательства. Доказательства содержат команду/метод, cwd, exit code, время, версию исходников и артефакт. Для визуальной проверки — полученное изображение и источник проверки. Утверждение Grok «я посмотрел» не заменяет артефакт. Для тестового графика: выполнить скрипт с сохранением PNG, приложить PNG и данные/проверку точки (0,0) и симметрии, затем передать ревьюеру с поддержкой изображений. Если изображение недоступно адаптеру — запросить конкретное действие пользователя и честно указать отсутствующее доказательство.

Ревью возвращает структурированный вердикт: принято, требуется исправление кода, нужны доказательства, нужен ответ пользователя. Отсутствие скриншота не запускает переписывание рабочего кода. Ошибка npm/PATH запускает восстановление проверки. Транспортная ошибка вызывает сверку статуса run и reconnect. Проверка результата Astra — read-only; запуск программы для получения артефакта выполняет worker/runner.

Вычисляемые правила исполняет Rust. Каждый шаг имеет устойчивый id и журнал. Повторное нажатие не создаёт второй run. После разрыва связи сначала выясняется состояние провайдера, затем продолжается работа. Разрешён один активный изменяющий run на worktree; параллельные чаты используют разные рабочие копии.

## 9. Техническая основа

Оставляем Tauri 2 + React/TypeScript для desktop UI и Rust/Tokio для логики. UI разбивается по функциям вместо одного `App.tsx`. Отдельные модули Rust: projects, chats, runs, providers, events, orchestration, credentials, context, rules, skills, validation, git/results, search, settings.

SQLite с миграциями: projects, chats, messages, runs, provider_sessions, run_events, artifacts, acceptance_checks, settings, instruction_snapshots. API key не в этих таблицах. Старые tasks/artifacts мигрируют в legacy-чаты с сохранением истории, путей и незавершённых состояний. Версии плана, исходников, diff и ревью связаны, старое одобрение не действует на новый код.

Управление run отделяется от UI-запроса: короткие команды start/stop/continue, затем подписка на события через Tauri IPC. События содержат project/chat/run/actor, локальный sequence, время, тип и schemaVersion. Надёжный журнал хранится перед публикацией; UI может дочитать события по sequence. Частые текстовые deltas объединяются небольшими пакетами, чтобы не перегружать SQLite и рендер.

Cursor adapter: долгоживущие agent/run handles, incremental Connect parser, durable replay, cancel, catalog и согласование ошибок. Поддержка `Send`, `ObserveRun`, `GetRun`, `CancelRun` задокументирована в [Cursor SDK services](https://github.com/cursor/sdk-bridge/blob/main/docs/services.md). Важная деталь восстановления: offsets live `Send` и durable `ObserveRun` не взаимозаменяемы; хранить их раздельно и убирать дубли при replay. См. [streaming semantics](https://github.com/cursor/sdk-bridge/blob/main/docs/streaming.md).

Codex adapter: постоянные threads, маршрутизация ответов/уведомлений, каталог, текстовые и reasoning-summary события, отмена, usage и восстановление сессии. Контракт строится по установленной версии app-server, experimental-поля включаются только при проверенной поддержке. Основание — [Codex App Server](https://learn.chatgpt.com/docs/app-server).

Capabilities запрашиваются при подключении: модели/effort, режимы, изображения, контекст, usage, cancel/resume/steer, поддержка инструкций. UI не рисует неподдерживаемые переключатели как рабочие. Например, локальный Cursor `GetUsage` в закреплённой proto помечен cloud-only: использовать доступные run-события, а отсутствие данных не интерпретировать как нулевой расход или бесплатность.

На Windows — корректное разрешение EXE/CMD, пути и остановка дерева процессов; на Linux — executable permissions, PATH и process groups. Timeout прекращает процесс, а не только ожидание результата. UI-закрытие и выход из приложения различаются: при работе можно свернуть в tray, явный выход останавливает run с сохранением состояния. После аварии приложение сверяет сохранённые ids с провайдером и не обещает продолжение погибшего процесса.

Worktree разделяет файлы задач, но не является OS sandbox. Ограничение Astra только чтением проверяется на уровне инструментов/провайдера. Профиль Grok показывает фактические полномочия. Собственный проект не подключает MCP и не должен случайно запускать унаследованные глобальные MCP-конфигурации; это отдельный тест изолированного профиля провайдера.

Поиск: SQLite FTS для сообщений и заголовков, локальный индекс имён/текстовый поиск по репозиторию с ignore-правилами. Полные логи и крупные артефакты хранятся на диске с метаданными в БД. Поиск и построение UI не вызывают Astra.

## 10. Этапы реализации и приёмка

Каждый этап заканчивается запускаемым результатом и проверкой сценария. Новая сборка содержит версию/commit в About. Внешний вид входит в готовность этапа, а не откладывается до конца.

| Этап | Работа | Проверяемый результат |
|---|---|---|
| M0. Подключения и сохранение | Credentials, автозагрузка настроек, фоновая проверка, capability probes, регрессионные сценарии известных ошибок | После трёх перезапусков ключ не вводится; каталог моделей читается; валидация продолжается без Cursor key; история доступна офлайн |
| M1. Новый UI и темы | Эталоны Cursor, дизайн-токены, sidebar/chat/composer/inspector, settings, белая/чёрная/системная темы | Пустой и работающий чат, настройки и diff выглядят согласованно в обеих темах; тема и панели сохраняются |
| M2. Проекты и постоянные чаты | Open/clone/create, схема данных и миграции, список чатов, архив, поиск заголовков, восстановление | Создать новый repo, добавить существующий и клонировать третий; открыть по два чата, перезапустить, продолжить правильный чат с той же рабочей папкой |
| M3. Работа в реальном времени | Event journal, streaming обоих провайдеров, markdown/tool cards, stdout, cancel, очередь, reconnect | Видеть действия до финального ответа; переключить чат во время run; отменить реально; после разрыва связи не получить второй run или дубли сообщений |
| M4. Модели и контекст | Picker по ролям, effort/Fast, упорство, budgets/compaction, usage, `@`-вложения и настройки по областям | Выбранные параметры видны в provider request snapshot; неподдерживаемые значения исключены; длинный чат сжимается без потери цели; estimations подписаны |
| M5. Rules и Skills | CRUD, импорт совместимых файлов, области и роли, активация, slash menu, instruction snapshots | Правило реально меняет поведение в своём scope; отключённое правило не применяется; skill вызывается вручную/по релевантности; после рестарта настройки прежние |
| M6. Полный рабочий цикл | Режимы Discuss/Plan/Agent, автоматические доработки, evidence, review, diff/artifacts, apply, checkpoints | Вопрос получает ответ без правок; дефект возвращается Grok; недостающая картинка собирается отдельно; принятый результат переносится в нужную ветку без потери пользовательских файлов |
| M7. Поиск, качество и выпуск | Полнотекстовый поиск, palette/shortcuts, производительность истории, Windows/Linux installer tests, release-сборки, документация | Все сценарии ниже проходят в установленном приложении на обеих ОС; нет зависимости от cwd разработчика или открытой PowerShell |

Последовательность: M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7. Если capability probe выявляет ограничение SDK, оно фиксируется до реализации зависимого контрола. Оценка сроков уточняется по результатам M0–M1; завершение привязано к проверкам, не к числу написанных экранов.

## 11. Обязательные проверки готовности v1

1. Ключ и тема переживают restart; подключение не является ежедневной формой.
2. Open, clone и create repository работают, включая новый repo без commits и dirty checkout.
3. Чаты и артефакты прежней v0.2 доступны после миграции.
4. «Дай краткий план» не изменяет файлы и не запускает Grok автоматически.
5. В Agent-режиме Astra планирует, Grok выполняет, пользователь видит реальные события обоих до конца run.
6. Stop отменяет выполнение, повторное нажатие не дублирует run; после сбоя восстанавливается корректная стадия.
7. Модель, effort, Fast, упорство и контекст либо реально применяются, либо недоступность ясно обозначена.
8. Rules/Skills влияют на правильный проект и роль; пользователь видит активный набор.
9. Тестовый Python-график проходит путь до ревью с реальным PNG; отсутствие доказательства не требует переписывать код.
10. Пользователь видит место сохранения программы, открывает файл/папку, просматривает diff и применяет итог в выбранный репозиторий.
11. Ошибки CLI, auth, rate limit и среды содержат конкретную причину и доступное действие; completed не означает просто «модель перестала отвечать».
12. Белая и чёрная темы, поиск, клавиатура и длинный чат проходят визуальную и функциональную приёмку.
13. Установленные release-сборки Windows/Linux работают из обычного launcher, с путями с пробелами и кириллицей, без development environment.

Тестовая стратегия: unit-тесты state machine/context/rule resolution; записанные протокольные fixtures для split frames, keepalive, duplicate replay и errors; интеграционные тесты с реальным Git/temp repos; UI-сценарии на mock providers; ограниченные live smoke-tests аккаунтов; финальная проверка desktop installer и обоих оформления на Windows/Linux. Тестовая задача на UI не расходует модели в каждом запуске CI.

Первый пользовательский результат нового плана — сохранённый ключ и нормальная оболочка с проектами и чатом. Финальный результат — полный управляемый путь от сообщения до проверенных и применённых файлов. Критерий «получили ответ Astra/Grok» больше не используется как критерий завершения продукта.
